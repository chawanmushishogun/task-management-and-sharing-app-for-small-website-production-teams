# Webサイト制作のスモールチームのための、権限設定のいらないタスク共有アプリ

## 1. サービス概要

- 3〜4人のWeb制作チームが、週1回の進捗確認の会議で使う社内専用のタスク共有ツール。会議ではサイドバーから案件を1つずつ開き、その案件のタスク一覧を見ながら進める。タスクを振られた本人が、その場で担当・期日・ステータスを直せる
- Asanaでは、管理者が編集権限を付与するまでメンバーが自分のタスクを編集できず、会議中に権限付与の作業が発生して会議が止まっていた。本アプリには権限という概念がなく、Basic認証を通った社内メンバー全員が、全案件を見て編集できる
- 画面は「案件ごとのタスク一覧」と、全案件横断の「全タスク」の2種類だけ、項目は案件・担当・期日・ステータス・メモの5つだけなので、**使い方を覚える手間がほとんどない**。これが一番のメリットだと考えている。全タスクは「この人はいま何件抱えているか」を見るリソース確認用。社外（外注・クライアント）に見せることは想定しない

---

## 2. このアイデアはどこから生まれたか

### 2-1. きっかけとなった体験・感情

会社で、社内メンバーのリソース状況を定期的に把握するために、タスク管理ツールとしてAsanaを利用している。週1回の進捗確認の会議では、各自がタスクを振られたら、自分に関係のあるタスクの期日などをその場で入力する運用にしていた。

ところがAsanaでは、管理者が事前にそのメンバーへ編集権限を付与していないと編集できない。会議の途中で「入力できません」となり、管理者である自分がその場で権限設定をする間、会議が止まる。これが一度ではなく何度も起きた。守りたい相手（社外の人）はそこにいないのに、権限の仕組みだけが毎回立ちはだかる、という理不尽さを感じた。

追い打ちをかけたのが費用だった。Asanaの契約更新の案内が届き、請求額（月あたり7,000円ほど）を改めて確認したとき、「この金額を払っているのに、自分たちが開いているのはタスク一覧と担当者・期日の確認だけだ」と気づき、もったいなさと違和感を覚えた。機能が多すぎて、自分たちの使い方では持て余しており、コストの割に十分に使いこなせていないという実感があった。

さらに、Chatworkなどの連絡ツールやDropboxのようなファイル共有ツールと役割が重なる部分があり、情報が複数のツールに分散してしまう懸念もあった。

### 2-2. なぜそれが「気になった」のか

余計な機能がついていないことに価値を感じる性分で、Asanaのように多機能で高額なツールを、使っていない機能ごと払い続けている状態に違和感があった。特に権限管理は「誰かを守るため」の仕組みのはずなのに、社内だけで使う自分たちにとっては誰も守っておらず、ただ会議を止めているだけだった。仕組みが目的から切り離されて残っている状態が気持ち悪く、自分で作れば「社内全員が同格」というルールだけで動くツールにできるはずだと考えた。

## 3. 課題の整理

### 3-1. 表に見えている困りごと

進捗確認の会議中に、メンバーが自分のタスクを編集できず、管理者による権限付与の作業で会議が止まる。それでいてAsanaの機能の大半は使っておらず、月額コストの割に活用度が低い。

### 3-2. 本当に解決したい課題は何か

- なぜ困る？　→　会議の目的は「社内のリソース状況を全員で確認し、各自が自分のタスクを更新する」ことなのに、ツールの権限設定に会議の時間と管理者の手が取られている
- なぜそれが困る？　→　権限は本来「見せてはいけない相手から守る」ための仕組みだが、社内メンバーだけで使う場には守る相手がいない。それでも仕組み上、管理者が毎回設定しないとメンバーは動けず、管理者が権限の番人になってしまっている
- なぜそれが困る？　→　「全員が全案件を見て、自分のタスクは自分で直す」というだけの使い方に、多機能・高額・権限管理つきのツールは不釣り合いで、ChatworkやDropboxとも役割が重なって情報が分散する。使わない仕組みのために、コストと手間を払い続けている

→ 本当に解決したい課題：**社内メンバーだけで進捗を共有したいスモールチームが、必要のない権限管理に会議の時間と管理者の手間を取られ、そのために身の丈に合わないツールとコストを払い続けている状態を解消したい**

## 4. 想定ユーザーについて

### 4-1. 想定しているユーザー

「この人」として思い浮かべているのは自分自身である。

- 年齢設定
  - 年齢：20〜30代
  - 理由：年齢そのものよりも「小規模なWeb制作チームで進行管理を担っている」という立場が本質。ただし20〜30代の制作者は自分でツールを選び直す裁量を持ちやすく、SaaSの乗り換えに抵抗が少ないため、この層が最初の利用者になりやすい
- 生活・状況設定
  - 生活・状況：Web制作会社で、3〜4人のメンバーと複数のクライアント案件を並行して進めている。自分でもコーディングをしながら、週1回の進捗確認で「誰がどの案件のどこまで終わっているか」を把握する役割を担っている。Asanaの管理者（有料プランの契約者・メンバー招待や権限設定をする人）も兼ねている
  - 理由：この立場の人は「進捗を把握したい」「会議を止めずに進めたい」「ツールの契約と権限を管理している」の3つを1人で抱えている。本アプリは権限設定を持たないので、会議中にメンバーが自分のタスクを直すとき、管理者の手を止めることがなくなる。把握に必要な項目（案件・担当・期日・ステータス・メモ）だけを一画面に並べ、進捗確認そのものも短くする
- 環境設定
  - 環境：Basic認証で守られたURLに、PCのブラウザからアクセスする。メンバーは全員PCで作業しており、スマホからの操作は想定しない
  - 理由：アカウント登録やログイン画面をなくし、URLとBasic認証だけで今日から使い始められるようにする。「メンバーを招待して権限を付与する」という管理作業そのものをなくすことで、導入のハードルを下げる

### 4-2. 自分とユーザーの距離

**自分自身**

自分が所属するチームで実際に使っているAsanaの使い勝手・コストに対する不満が出発点であり、自分自身が最初のユーザーになる。

### 4-3. 実際に使われる可能性について（需要・存在確認）

- まず最初に使ってくれそうな人：自分が所属するスモールチームのメンバー
- どんな場面で思い出すか：週次・月次でタスク状況を確認し合うタイミング
- 今の生活の中で代わりに使っているもの：Asana（＋Chatwork、Dropboxで役割の一部を補完）
- 置き換えてまで使う理由：会議中に権限付与で止まらないこと。メンバーを追加した瞬間から全員が全案件を編集できる。画面が2種類・項目が5つしかないので、使い方や設定を学ぶ時間がいらない。結果として月額コストもなくなる

### 4-4. ユーザーがサービスを導入して利用するまでのイメージ

- きっかけ：Asanaの契約更新・見直しのタイミング
- 最初の一歩：チームにURLとBasic認証の情報を共有するだけ（アカウント登録不要）
- 使い続ける理由：週1回の会議が「案件を順に開いて、各自が自分のタスクを直す」だけで終わる。項目が案件・担当・期日・ステータス・メモの5つしかないので、誰が開いても迷わない。この状態が続くこと自体が、使い続ける理由になる

**toB向けサービスとしての観点**

- 企業・組織が導入を判断する理由：導入を判断するのは自分が所属するチーム自身であり、判断者と開発者が同じ人物。判断材料は「Asanaの月額（約7,000円）がゼロになる」「使う機能が減ることで運用が楽になる」の2点で、比較検討の相手は自チームのメンバーだけ。まず自分のチームで実運用し、そこで成立することを確かめる
- 機密情報・業務データを登録してもらえるか：登録するのは案件名・担当者名・期日・ステータス・短いメモだけに絞り、成果物ファイル・クライアントの連絡先・金額といった機密情報は扱わない（それらはこれまで通りDropbox／Chatworkに置く）。さらにSupabaseはオープンソースでセルフホストできるため、実運用の段階では社内NASにデータを置き直す道を残している。「外部に置くのは進捗の骨組みだけ」「最終的には手元に置ける」の2段構えで、個人開発サービスにデータを預ける不安を下げる
- 既存の運用・ツールから乗り換えるハードル：Asanaに蓄積した過去案件のデータは移行せず、新しく始まる案件から本アプリに登録する。契約更新のタイミングまでAsanaと並行運用し、「進捗確認の場でこちらだけ見れば足りる」状態になったらAsanaを解約する。データ移行作業をなくし「新規案件からの切り替え」にすることで、乗り換えのハードルを下げる

## 5. 既存サービス・競合調査

### 5-1. 似たサービスの調査

- サービス名：Asana
- URL：https://asana.com/ja
- どんなことができるか：タスク・プロジェクト管理、ガントチャート、ワークフロー自動化、レポート機能、多数の外部連携など、非常に多機能。起点は個人の画面（ホーム／マイタスク）で、他のメンバーのタスクを全案件横断で見る画面は標準にはなく、検索で条件を組むか、有料プランの「ワークロード」を使う。サイドバーにはホーム・マイタスク・受信トレイ・レポート・ポートフォリオ・ゴール・チームごとのプロジェクトが並び、覚える画面と概念が多い

### 5-2. それでも自分が作りたい理由

一番のズレは権限の仕組みだった。Asanaは、社外の人や大きな組織が混在する前提で「誰が何を見られるか・編集できるか」を細かく制御できるようになっている。それ自体は正しい設計だが、自分たちは社内の3〜4人だけで、全員が全案件を見て自分のタスクを直す、という使い方しかしない。守る相手がいないのに、管理者が編集権限を付与するまでメンバーは自分のタスクすら編集できず、会議の途中で権限設定のために手が止まる。「機能が足りない」のではなく「自分たちには要らない仕組みが外せない」ことが不満だった。

もう1つ、会議で実際に困っていたのが画面の迷子だった。Asanaのサイドバーは項目が多く、案件はチームの下に畳まれている。会議中に案件を切り替えて話しているうちに「いま見ている案件はどこだったか」を見失い、探す時間が発生していた。

こうした摩擦は、Asana側の設定を整えれば減らせるものもある。メンバー追加時の既定の権限を編集可にしておく、サイドバーの表示項目を減らす、担当者別の検索を保存しておく、といった手はある。ただ、そのためには管理者がAsanaの設定の仕組みを学んで整える必要があり、一部は有料プランの機能になる。進捗確認という本来の目的とは関係のないところに学習コストがかかる。設定を何もしなくても最初からその状態になっていること、そして覚えることが少ないこと自体に価値があると考えた。

加えて、機能が多すぎて自分たちの使い方に対しては過剰であり、月あたり7,000円ほどのコストに見合うだけの活用ができていなかった。ChatworkやDropboxと役割が重なる部分があり、情報の置き場所が分散してしまうことにも違和感があった。

### 5-3. 差別化を「体験価値」で表現する

- ❌「タグ機能がある」「ガントチャートがある」ではなく
- ⭕「進捗確認の会議で案件を順に開いていくとき、タスクを振られた本人がその場で自分の期日を入れられる。権限付与で会議が止まらない」「サイドバーは全タスクと案件の一覧だけなので、案件を切り替えながら話しても今見ている案件を見失わない」「画面が2種類・項目が5つしかないので、初めて開いたメンバーでも使い方を覚える手間がほとんどない」「『この人はいま何件抱えているか』は、全タスク画面で担当者を絞ればすぐ見られる」

このアプリは、【社内メンバーだけで進捗を共有するWeb制作のスモールチーム】の【週1回の進捗確認の会議で、各自が自分のタスクをその場で更新する瞬間】を助けるアプリです。
- 私のアプリの差別化ポイント：Asanaと同じ「タスク・担当・期日・ステータス」を扱いながら、社内メンバーだけで使うチームには要らない仕組みを設計の段階で外し、学習コストを最小にしたこと。1つ目は権限。Asanaは「誰に何を見せるか」を細かく制御できるが、社内メンバーだけで使う限り、その制御は安全装置ではなく会議を止める摩擦にしかならない。本アプリではBasic認証の内側は全員が同格で、見えないタスクも編集できないタスクも存在しない。2つ目は覚えることの少なさ。サイドバーは全タスクと案件の一覧だけ、画面は案件ごとのタスク一覧と全タスクの2種類、項目は案件・担当・期日・ステータス・メモの5つで、Asanaのように使い方や設定を学ぶ時間がいらない。3〜4人のチームでは「ツールを覚える」こと自体がコストなので、ここが一番のメリットだと考えている。全タスク画面は、会議のためではなく「この人はいま何件抱えているか」を見るリソース確認用に持つ。その代わり、社外（外注・クライアント）に見せることは最初から想定せず、用途を「社内の進捗共有とリソース確認」に絞っている。「登録不要でURLを共有した日から使える」といった軽さは、この設計の帰結であって、それ自体が売りではない

## 6. このサービスで提供したい価値

### 6-1. ユーザーの変化

- 行動の変化：会議中に「入力できません」「ちょっと待って、権限つけます」のやりとりがなくなり、各自が自分のタスクをその場で直す。進捗確認は案件を順に開いて各自が直すだけで済み、結果としてAsanaを解約できる
- 気持ちの変化：管理者が「権限の番人」でなくなり、会議を止める側から進める側に戻れる。メンバーも、自分のタスクを直すのに誰かの許可を待たなくてよくなる。サイドバーが全タスクと案件だけなので、会議中に「いまどの案件を見ていたか」を見失う不安がなくなる
- 考え方の変化：権限管理は「守る相手がいるときだけ要る仕組み」だと捉えるようになる。「機能が多い＝良いツール」ではなく「自分たちの使い方に対して、余計な仕組みが外せるか」で選ぶようになる

### 6-2. 価値を一文で表す

「このサービスは、社内メンバーだけで進捗を共有するWeb制作のスモールチームが、権限設定に煩わされることなく、会議の場で全員が自分のタスクをその場で更新できるようになるサービス」

## 7. このアプリで実現すること

### MVPで作る機能

- 権限設定なし（Basic認証を通ったメンバー全員が、全案件を閲覧・編集できる。これは機能ではなく設計上の決定）
- Web制作の定番工程（企画/情報設計/PM・デザイン・コーディング・メタタグ系入力・CMS/バックエンド・素材/関連情報・公開）をテンプレートにした案件作成（実装済み）
- テンプレートに当てはまらない小さな仕事を置く「その他案件」（案件単位で自由に追加）
- プロジェクトごとのタスク一覧（リスト表示／ボード表示）
- 全プロジェクト横断の「全タスク」画面、担当者フィルタ
- 担当者・期日・ステータス・備考の編集
- メンバーの追加・編集
- Basic認証によるアクセス制限
- Supabaseによるデータ永続化（複数人・複数端末での共有）

※ Supabaseによる永続化は自分にとってキャッチアップが必要な要素だが、これをMVPから外すとデータがブラウザ単位になり、「お互いのタスク状況を把握する」という核の体験そのものが検証できなくなる。そのためMVPに含める。逆に、リアルタイム同期・ログイン・タスク削除などは核の検証には不要なので本リリースに回す。

### 本リリースで作る機能

- ログイン機能（Basic認証からの発展）
- タスクの状況全体を1つのテキストファイルとして出力し、Obsidianなどに書き出せる機能（未実装。App→Obsidian方向のエクスポートであり、Obsidian側からの取り込みではない）
- リアルタイム同期（同時編集の即時反映）
- タスクの削除・サブタスク・コメント（要否は運用しながら判断）

## 8. このアプリの懸念点とその対策

### 懸念点①：同時編集時のデータ競合

- 何が問題になりそうか：複数人が同じタスクを同時に編集した場合、どちらの変更が反映されるか
- なぜそう思うか：本アプリには「手番」のような排他制御の仕組みがなく、誰でも自由なタイミングで編集できるため
- そのために考えている対策：まずはlast write wins（後から保存した内容が勝つ）で割り切る。小規模チームの用途であれば実運用上大きな問題にはなりにくいと考え、困ってから精緻化する

### 懸念点②：Basic認証だけでは業務データを守りきれない

- 何が問題になりそうか：Basic認証が守るのは画面（URL）だけで、ブラウザからSupabaseに接続するための公開キーはページのコードに含まれる。キーを知っている人がAPIを直接叩けば、画面を経由せずにデータを読み書きできてしまう
- なぜそう思うか：SupabaseはブラウザからDBへ直接アクセスする構成が前提で、アクセス制御はDB側のRow Level Security（RLS）で行う設計になっているため。Basic認証を付けただけでは、この層が空いたままになる
- そのために考えている対策：「画面に入れるか」ではなく「DBが誰に何を許すか」をDB側で決める。具体的には次の4つ
  - 全テーブルでRLSを有効にし、ポリシーがない状態（全拒否）から始める。anonロールには読み書きを一切許可しない
  - Supabase Authでチーム共有の1アカウントにログインし、「authenticatedロールのみ読み書き可」というポリシーだけを置く。社内3〜4人で権限を分けない設計なので、MVPではこの1本で足りる
  - service_roleキーはフロントに置かず、Supabaseの管理画面でしか使わない。anonキーとURLは.envに置き、リポジトリがPublicなので.envはGit管理から除外している
  - 通信はVercelのHTTPS。預けるデータを案件名・担当・期日・ステータス・メモに限定し、成果物・連絡先・金額は置かない（4-4参照）
- この構成の限界：共有アカウントなので人単位で締め出せない。退職時はBasic認証と共有アカウントのパスワードを両方変える運用にし、本リリースで個人ログインに移行して解消する。中の人の誤操作・悪意には対策がなく、誰が変えたかも追えない。これは懸念点③と同じく本リリースの変更履歴で対応する
- 確認の基準：「画面から動くか」ではなく「画面を通さずにAPIを直接叩いたときに弾かれるか」。テーブルを足すたびに、anonキーでREST APIを直接叩くテストをセットで行う

### 懸念点③：権限がないことで、他人のタスクを誤って書き換えてしまう

- 何が問題になりそうか：全員が全案件を編集できるため、担当者でない人が誤操作で期日やステータスを変えてしまい、誰が変えたか分からなくなる
- なぜそう思うか：権限を外すことが本アプリの核なので、「編集できないようにする」という対策は取れない。誤操作を防ぐのではなく、起きたときに気づけるようにする必要がある
- そのために考えている対策：MVPでは3〜4人で毎週画面を見るため、変わっていれば会議の場で気づけると考え、対策を入れない。本リリースで「誰がいつ何を変えたか」の変更履歴を残すことを検討する。権限で縛るのではなく、履歴で追える形にすることで、設計の核を保ったまま安心を足す

## 9. 今後の展開・発展の方向性

### 使い続ける理由と、データが溜まったときの価値

- ユーザーはなぜ使い続ける？：週1回の会議が「この画面を開いて、各自が自分のタスクを直す」だけで終わる状態が続く限り、他のツールに戻る理由がなくなる
- データが溜まると何ができる？：担当者ごと・案件ごとのタスクと期日が同じ形で溜まっていくので、「誰にどれくらい仕事が集中していたか」「どの工程で期日がずれやすいか」を後から振り返れる。本アプリの目的である社内のリソース確認を、その週だけでなく期間で見られるようになる
- 運用・仕組みで価値を出せないか：Asana解約後の経常コスト削減額を数字で見せることで、「必要な分だけで十分」という判断を社内で共有しやすくする

### 今考えている発展案

- 機能追加の方向性：変更履歴（誰がいつ何を変えたか。懸念点③の対策）。工程テンプレートの編集（チームの実務に合わせて工程・タスクを育てられるようにする。現在はコード内に固定）。アプリ内のタスク状況全体を1つのテキストファイルにまとめて出力し、Obsidianなどに書き出せる仕組み（未実装。会議後の記録を自分のメモに残す用途）。ログイン機能の追加
- UI・体験の改善：ガントチャート（期日を期間で持っているため実装は可能。実際に必要になった場合に着手）
- 機能以外の工夫：担当者ごとの負荷の偏りを期間で振り返れるようにし、次の案件の担当割り振りに活かす

## 10. 技術スタック（手段としての技術）

### 10-1. 使用予定の技術

- フレームワーク：React + TypeScript + Vite（フロントエンド）
- DB／バックエンド：Supabase
- デプロイ先：Vercel（卒業制作・ポートフォリオ用の公開先）／将来的に社内NASへ移行予定（実運用用）
- 使用予定ライブラリ：Tailwind CSS（スタイリング）、lucide-react（アイコン）、@supabase/supabase-js（DB接続）。shadcn/uiのコンポーネント一式がFigma Makeの出力に同梱されているが、現時点では画面から使っておらず、必要になった部品（ダイアログ・セレクトなど）だけ使う方針

### 10-2. 技術選定の比較検討

フロントエンドについて：

| 候補 | 採用/不採用 | 理由 |
| --- | --- | --- |
| React + TypeScript + Vite | 採用 | 本アプリは「一覧上でその場編集」「リスト／ボード切替」「ドラッグ&ドロップ」など画面側の状態が多く、SPAとして作るのが自然。画面はFigma Makeの出力を土台にすでに一通り動いており、フロントの実装コストは支払い済み。残る作業をDB接続に集中できる |
| Ruby on Rails（Hotwire） | 不採用 | カリキュラムで学んだ技術で情報も多いが、画面側の状態が多い本アプリではJavaScriptの比重が大きくなり、Railsのビュー＋Hotwireで組むより素直にReactで状態を持つほうが見通しがよい。またフロントを作り直す工数がかかる。Railsで学んだMVCとDB設計の考え方は、Supabase側のテーブル設計に活かす |

DB／バックエンドについて：

| 候補 | 採用/不採用 | 理由 |
| --- | --- | --- |
| Supabase | 採用 | DB・API・認証・リアルタイム同期がセットで提供され、Express/WebSocketを自分で書かずに済む。オープンソースでDocker運用も可能なため、将来的に自前サーバー（NAS）へ移す道も残せる |
| Synology NASで自前（Express + WebSocket + DB） | 不採用（現時点） | データを手元に残せる利点はあるが、外部からの接続経路（VPN／QuickConnect／ポート開放／証明書）が最大の壁になり、NASが落ちるとアプリごと止まってしまう。何より、講師レビューや採用担当者など社外の人がアクセスできず、卒業制作としては成立しない |

デプロイ先についても同様の理由でVercel（またはCloudflare Pages）を採用した。

| 候補 | 採用/不採用 | 理由 |
| --- | --- | --- |
| Vercel / Cloudflare Pages | 採用 | git pushだけでHTTPS付きの外部URLが得られ、社外の人（講師・採用担当者）が実際にアクセスして試せる。無料枠で十分。Basic認証も簡単に設定できる |
| 社内NAS | 不採用（卒業制作としては） | データを完全に手元に置ける利点はあるが、社内ネットワークの外からはアクセスできず、外部レビューが必要な卒業制作の用途には合わない。実際に会社で本運用する段階で、Supabaseのセルフホスト版をNAS上にDocker運用し直す形で移行する予定 |

- 今回チャレンジしたい点：Reactでの状態管理（state設計）。以前作った別アプリ（オセロ）ではサーバー・WebSocket通信を学んだため、今回はその手前の「画面の状態をどこに置くか」を重点的に学びたい
- 不安な点：手番のない同時編集の衝突制御（オセロでは「手番」があったため発生しなかった問題）

### 10-3. キャッチアップ不足の懸念

現時点ではフロントエンド（React/TypeScript/Vite）のみで実装済み（localStorage保存）。React/TypeScriptはカリキュラム外の技術だが、Figma Makeが生成した1,600行超のApp.tsxを読み解き、カスタムフックとコンポーネントに分割する作業を通じて、state設計とコンポーネント分割は一通り手を動かしている。Reactの基本操作ごとのキャッチアップ状況は以下の通り。

| 項目 | 状況 | 具体的に何をしたか |
| --- | --- | --- |
| 状態管理 | 習得済み | useState と自作フック（useTasks / useProjects / useMembers）で実装。Figma Make が出力した1,600行超の App.tsx にあった40個以上の useState を「誰がその状態を見るか」で仕分けし、複数画面が見るものはフックへ、1つのコンポーネントしか見ないものはそのコンポーネント内へ下ろした。3画面（リスト／ボード／全タスク）から同じタスクを編集しても同じデータが変わる構造になっている |
| フォーム | 習得済み（基本） | 案件・タスクの追加モーダル、タスク名・プロジェクト名のインライン編集を自作の制御コンポーネントで実装。日本語入力（IME）の変換確定 Enter を送信と区別する対応も済み。react-hook-form などのライブラリは未使用 |
| ルーティング | **未着手** | 画面の切り替え（全タスク／プロジェクト／メンバー）は state で行っており、URL は変わらない。react-router は同梱されているが未使用。MVP は画面3つの切り替えで足りるため必須ではないが、「案件ごとのURLを共有する」用途で本リリースまでに導入を検討する |
| API連携 | **未着手** | 現在は localStorage への読み書きのみで、fetch も Supabase クライアントも未使用。ここが最大のキャッチアップ対象 |
| セキュリティ（RLS・認証） | **未着手** | バックエンドを置かずブラウザから Supabase に直接つなぐ構成なので、Rails ならフレームワークが担う「誰に何を許すか」を DB 側の RLS と Supabase Auth で自前で担保する必要がある。認識と対策は懸念点②に記載。テーブル作成時に RLS 有効・全拒否の状態から始め、anon キーで API を直接叩いて弾かれることを確認してからポリシーを足す順で進める |

したがってキャッチアップの懸念は、Reactそのものよりも API連携（Supabase）とそのセキュリティ、ルーティングに絞られる。Supabase導入によるDB・認証部分は未着手で、キャッチアップに一定の時間がかかることが見込まれる。まずはタスクデータの読み書きだけをSupabaseに差し替え、動作確認できた段階でメンバー・プロジェクトのデータも移行する、と段階を分けて進める。
