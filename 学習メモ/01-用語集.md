# 01. 用語集

React と TypeScript の言葉を、このアプリの実物と対応させて説明する。
**上から順に読むと積み上がる**ように並べてある。詰まったらここに戻る。

---

## SPA（Single Page Application）

**HTML が1枚しかないアプリ**のこと。

Rails では、`/users` を開くと `users/index.html.erb` から HTML が作られ、
`/users/3` を開くとまた別の HTML がサーバーで作られて返ってくる。
**ページを移動するたび、サーバーに聞きに行く**。

このアプリの `index.html` は、中身がほとんど空っぽ。

```html
<div id="root"></div>
```

この空の箱に、JavaScript が**全部の画面を後から作って入れる**。
リスト表示もボード表示もメンバー画面も、サーバーに聞かずに切り替わる。

そもそもこのアプリには**サーバーが存在しない**。
`npm run dev` で立ち上がるものは、開発中にファイルを配るだけの仮の窓口で、
Rails のような「リクエストを処理する場所」ではない。

---

## コンポーネント

**画面の部品**。見た目と振る舞いをセットにしたもの。

Rails の部分テンプレート（`_form.html.erb` のようなパーシャル）に近いが、
**動きも一緒に持っている**点が違う。

実体は**ただの関数**。HTML のようなものを返す。

```tsx
// src/app/components/StatusSelect.tsx（簡略版）
export function StatusSelect({ status }) {
  return <select value={status}>...</select>;
}
```

これを他の場所でタグのように書くと、その場所に部品が置かれる。

```tsx
<StatusSelect status={task.status} />
```

**関数名は大文字で始める**決まりがある。
小文字だと React が「ただの HTML タグ」だと思ってしまう。

このアプリの部品は `src/app/components/` にある。

---

## JSX

**JavaScript の中に HTML のような書き方を混ぜられる記法**。

```tsx
return <div className="flex">タスクがありません</div>;
```

これは文字列ではなく、JavaScript の式として扱われる。
だから `{}` で囲めば、途中に値や計算を差し込める。

```tsx
<span>{members.length}名のメンバー</span>
```

`.erb` の `<%= %>` とほぼ同じ役割が `{}` だと思えばよい。

注意点が2つある。

- `class` ではなく **`className`**（`class` は JavaScript の予約語なので使えない）
- 閉じタグを省略できない（`<br>` ではなく `<br />`）

---

## state（状態）★最重要

**いまの画面がどうなっているかを覚えている変数**。

そして React では、**state を書き換えると画面が自動で描き直される**。
ここがすべての中心。

### なぜ普通の変数ではダメなのか

たとえば「サイドバーが開いているか」を普通の変数で持ったとする。

```tsx
let expanded = true;          // 普通の変数

function 閉じるボタンが押された() {
  expanded = false;           // 変数は false になる
}                             // …でも画面は何も変わらない
```

変数の中身は確かに変わる。だが**画面はそれを知らない**。
誰も「変わったから描き直せ」と教えていないから。

Rails ならページごとサーバーから作り直すので、この問題は起きない。
React は画面を作り直さずに動き続けるので、**変化を伝える仕組みが要る**。

それが `useState`。

```tsx
const [expanded, setExpanded] = useState(true);

function 閉じるボタンが押された() {
  setExpanded(false);         // ← React に「変わった」と伝わる
}                             //    → React が画面を描き直す
```

### 書き方の読み方

```tsx
const [expanded, setExpanded] = useState(true);
//     ↑いまの値   ↑変える関数              ↑最初の値
```

`useState` は**2つ組**を返す。左が中身、右がそれを変える関数。
名前は自由だが、`x` と `setX` にするのが慣習。

**直接代入してはいけない**。必ず右側の関数を通す。

```tsx
expanded = false;      // ✗ 画面が更新されない
setExpanded(false);    // ○
```

### このアプリの実例

`src/app/App.tsx` にこう書いてある。

```tsx
const [filterStatus, setFilterStatus] = useState<Status | "all">("all");
```

「いまどの絞り込みが選ばれているか」を覚えている state。
`"all"` から始まり、ユーザーが「進行中」を押すと `setFilterStatus("in_progress")` が
呼ばれ、画面が描き直されて、進行中のタスクだけが並ぶ。

**この state を消すと、絞り込みボタンは押しても何も起きなくなる。**

---

## 再レンダリング

**state が変わったので、React が画面を作り直すこと**。

ここで初心者が必ず驚くのが、

> **コンポーネントの関数は、何度も繰り返し呼ばれる**

ということ。Rails のビューは1リクエストにつき1回だけ実行されるが、
React のコンポーネントは state が変わるたびに何度でも呼ばれる。
1回の操作で何十回も呼ばれることがある。

だから、コンポーネントの中に「1回だけやりたい処理」を素直に書くと壊れる。
（そういうものは `useEffect` という別の仕組みに入れる。
　→ このアプリでは `useLocalStorage.ts` で使っている）

React は毎回全部を作り直しているように見えて、
実際には**前回との差分だけ**を本物の画面に反映している。だから速い。

---

## props（プロパティ）

**親のコンポーネントから子へ渡す値**。関数の引数と同じもの。

```tsx
// 渡す側（親）
<StatusSelect status={task.status} onChange={...} />

// 受け取る側（子）
export function StatusSelect({ status, onChange }) { ... }
```

大事な決まりが1つある。

> **props は子から書き換えられない。** 上から下への一方通行。

子が「変えたい」ときは、**親からもらった関数を呼ぶ**。

```tsx
// 子は自分でデータを変えず、渡された関数を呼ぶだけ
<StatusSelect onChange={status => onUpdateStatus(task.id, status)} />
```

これで「データは下る、お願いは上る」という流れになる（→ 一方向データフロー）。

---

## 一方向データフロー

このアプリ全体の骨格。

```
      App.tsx（tasks を持っている）
        │
        │ ① データを下へ配る（props）
        ▼
      ListView ── 各行 ── StatusSelect
        │
        │ ② 「これを変えて」と関数を呼んで上へ知らせる
        ▲
      App.tsx が state を書き換える
        │
        │ ③ React が画面を描き直す
        ▼
      新しい内容で表示される
```

**データを持っている場所は1か所だけ**。
だから、リスト表示で担当者を変えてもボード表示に反映されるし、
食い違いようがない。

Rails でいえば「DB が唯一の正解で、どの画面もそこを見ている」のと同じ発想。
このアプリではその DB の役割を、App が持つ state が担っている。

---

## リフトアップ（状態の持ち上げ）

**2つ以上の部品が同じ値を見る必要があるなら、共通の親に置く**という原則。

- `tasks` … リスト・ボード・全タスクの3画面が見る → **App（フック）に置く**
- 「この行のメニューが開いているか」… その行しか見ない → **その部品の中に置く**

判断基準はひとつ。

> **その値を知る必要があるのは誰か。**

このアプリは最初、開いているメニューの ID まで App が覚えていた。
必要なのはその行だけだったので、部品の中へ下ろしたら state が20個以上消えた。

---

## フック（Hook）

**`use` で始まる関数**のこと。React の機能を借りるための入り口。

- `useState` … 状態を持つ
- `useEffect` … 「変わったときに1回やる」処理を書く
- `useRef` … 画面の更新と関係ない値を覚えておく

決まりが1つある。

> **コンポーネントの一番外側で、毎回同じ順番で呼ぶこと。**
> `if` の中や `for` の中で呼んではいけない。

React は「何番目に呼ばれたか」で state を見分けているため、
順番が変わると別の state を掴んでしまう。

---

## カスタムフック

**自分で作ったフック**。`use` で始まる名前にした、ただの関数。

このアプリの `src/app/hooks/useTasks.ts` がそれ。

```tsx
export function useTasks() {
  const [tasks, setTasks] = useLocalStorage<Task[]>("tasks", INITIAL_TASKS);

  function updateTask(id, patch) { ... }
  function addTask(input) { ... }

  return { tasks, addTask, updateTask, ... };
}
```

**データ（`tasks`）と、それを操作する関数を1か所にまとめたもの。**
Rails のモデルに近い立ち位置。

これを作る一番の理由は、**あとで中身を差し替えるため**。
いまは localStorage に保存しているが、将来 Supabase（DB）に移すとき、
書き換えるのは `useTasks.ts` の中だけで済む。
呼んでいる画面側は1行も触らなくていい。

> 先に境界を引いておくと、あとで効いてくる。

---

## TypeScript と「型」

JavaScript に**「この変数には何が入るか」の宣言を足したもの**。

```ts
// src/app/types.ts
export interface Task {
  id: string;
  name: string;
  assigneeId: string | null;   // 文字列 か null のどちらか
  completed: boolean;
  status: Status;
}
```

Rails の `schema.rb`（テーブルの列の定義）に近い。
違うのは、**DB ではなくコードのために書く**という点。

型を書いておくと、コードを書いている最中に間違いが分かる。

```ts
task.complete       // ✗ そんな名前はない、と怒られる（正しくは completed）
task.completed = 1  // ✗ boolean に数値は入らない
```

これを機械的に全部調べるのが `npm run typecheck`。
**動かす前に間違いが見つかる**のが最大の利点。

よく出てくる書き方：

| 書き方 | 意味 |
| --- | --- |
| `string \| null` | 文字列か null のどちらか（`\|` は「または」） |
| `Task[]` | Task の配列 |
| `Partial<Task>` | Task の項目を「一部だけ」持つもの。更新のときに使う |
| `"list" \| "board"` | この2つの文字列しか入らない |
| `?` （`initial?: Member`） | あってもなくてもよい |

### `.ts` と `.tsx` の違い

JSX（HTML のような書き方）を含むファイルは **`.tsx`**、
含まないものは **`.ts`**。中身のルールは同じ。

## localStorage

**ブラウザが持っている小さな保存場所**。

このアプリには DB もサーバーもないので、ここにデータを置いている。

- 閉じても消えない
- **文字列しか入らない**（配列を入れるときは JSON に変換する）
- **そのブラウザの中だけ**。別のブラウザ・別のPCからは見えない
- 容量に上限がある（アバター画像を入れすぎると溢れる）

このアプリでは `src/app/hooks/useLocalStorage.ts` が
`useState` とほぼ同じ書き味で使えるように包んである。

```tsx
const [tasks, setTasks] = useLocalStorage<Task[]>("tasks", INITIAL_TASKS);
//                        ↑ useState とそっくりだが、変えると勝手に保存される
```

保存されているキーは DevTools（F12）→ Application → Local Storage で見られる。
`asana-clone:tasks` のように、頭に `asana-clone:` が付いている。
（他のアプリと名前がぶつからないようにするため）

---

## Vite（ヴィート）

**開発用サーバーと、本番用の組み立て役**。

- `npm run dev` … 開発用に起動。ファイルを保存すると画面が勝手に更新される
- `npm run build` … 本番用に、たくさんのファイルを数個にまとめる

ブラウザは `.tsx` も TypeScript も読めない。
**ただの JavaScript に翻訳して届ける**のが Vite の仕事。

Rails の Asset Pipeline / esbuild にあたる。

なお `npm run build` は `tsc --noEmit && vite build` という2段構えになっている。
**Vite は型を見ないで翻訳してしまう**ので、先に `tsc`（型チェック）を通している。

# ── ここから下は「まだこのアプリに無い」言葉 ──

いまのアプリはサーバーを持たず、localStorage に保存している。
下の語は、**保存先をみんなで共有できる形にするとき**に出てくる。
くわしくは [06-サーバーとDBの話.md](06-サーバーとDBの話.md) で使う。

---

## サーバー

**ずっと起動していて、みんなが同じ場所に読み書きしに行くコンピュータ**。

「サーバー」という言葉は2つの意味で使われるので注意する。

- **機械**としてのサーバー（Render のマシン、NAS など）
- そこで動く**プログラム**としてのサーバー（Express で書いたもの）

このアプリでいま「サーバーがない」と言うのは、後者のこと。
ブラウザの中だけで動いていて、データを預ける相手がいない状態。

Rails アプリは、それ自体がサーバー（プログラム）。
このアプリはブラウザで動く SPA なので、
共有したいなら**別に**サーバーを立てる必要がある。

---

## API（エンドポイント）

**サーバーに用意された、用途ごとの窓口**。

ブラウザは DB を直接いじれないので、
「タスク一覧をください」「このタスクを更新して」といった
お願いを、この窓口に投げる。

```
GET  /tasks         タスク一覧をください
POST /tasks         新しいタスクを1件作って
PATCH /tasks/:id    このタスクをこう変えて
```

この一つ一つの窓口が API（エンドポイント）。
`GET` `POST` `PATCH` `DELETE` は「読む・作る・変える・消す」の合図で、
Rails のルーティングで見た HTTP メソッドと同じもの。

Rails の `routes.rb` ＋ Controller のアクションが、
だいたいこの「API を並べる」作業にあたる。

---

## Express（エクスプレス）

**Node.js で、この HTTP の窓口を作るための道具**。

Rails でいうと、**ルーティングと Controller の入り口だけ**を
取り出したもの。Model も View も持っていない（そこは自分で書く）。

```js
const app = express();
app.get("/tasks", (req, res) => { ...DBから読んで返す... });
```

このアプリではまだ使っていないが、
**オセロ（yukkuri-reversi）では既に使っている**。
そこでの仕事は「ビルド済みの画面ファイルを配る」ことだった。
タスク管理では、これに「データを読み書きする窓口」を足すことになる。

---

## WebSocket（ウェブソケット）

**サーバーとブラウザをつなぎっぱなしにして、
どちらからでも話しかけられるようにする仕組み**。

- **HTTP** = 手紙。1回お願いして、1回返事が来て、切れる。
  サーバーから勝手に話しかけられない。
- **WebSocket** = 電話をかけっぱなし。
  繋いだままにして、どちらからでも好きなときに喋れる。

「他の人が編集した内容を、こちらが何もしなくても画面に出す」には
これが要る。HTTP だけだと、リロードしないと最新にならない。

これもオセロで使っている（対戦相手の着手をリアルタイムに配る部分）。
Express が作ったサーバーに**相乗り**する形で動く。

---

## DB（データベース）

**データを、消えない形で、たくさん貯めておく場所**。

いまこのアプリは localStorage を DB 代わりにしているが、
localStorage は「そのブラウザの中だけ・容量が小さい・
みんなで共有できない」ので、本来の用途には向かない。

本物の DB（PostgreSQL、MariaDB など）はサーバーの隣に置き、
**サーバー経由でのみ**読み書きする。
ブラウザから直接は繋がない（言葉が通じないし、パスワードが漏れる）。

Rails の DB とまったく同じ役割。
違うのは、このアプリでは DB と話す部分（Model 相当）を
自分で用意する必要がある、という点。

---

## Supabase（スーパベース）

**「DB ＋ API ＋ リアルタイム同期 ＋ 認証」がセットになったサービス**。

上に出てきた Express・WebSocket・DB を**自分で書かずに済ませる**選択肢。
窓口（API）も、リアルタイム配信も、最初から用意されている。

自前でサーバーを立てるか、Supabase に任せるかは、
このアプリの次の分かれ道。→ [06-サーバーとDBの話.md](06-サーバーとDBの話.md)
